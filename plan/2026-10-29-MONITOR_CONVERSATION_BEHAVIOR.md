# Monitor conversation behavior

- Events remain chronological. Selecting a row reveals one connector and dots for its visible related events. No connector is shown before selection.
- Conversations group retained events by conversation, with each group and its rows ordered by newest event sequence. A new event brings its group to the top. This view has no links gutter or conversation filter.
- Events offers a conversation filter beside Search. Its active state is one dismissible button. Switching to Conversations removes that transient filter. Type/search filters still apply.
- Conversation metadata is local to Monitor's bounded, in-memory history. It is separate from `session_id`, which identifies a single API request. Related scans/steps inherit the request's conversation metadata, including steps captured before correlation finishes.
- Explicit `extensions["localrouter.session"].id` values (including the gateway's normalized caller session headers) are scoped to the authenticated client. `reset` starts a new epoch. The UI receives an opaque local ID, not the caller's raw ID.
- Responses can continue via `previous_response_id` when the referenced response remains captured. Otherwise message-history correlation requires an exact retained message prefix followed by assistant/tool continuation, scoped to one client. Identical prompts/history alone are never joined. Ambiguous candidates start a separate group. Transport sessions, timing, client identity alone, and routing policy fingerprints do not establish a conversation.
- Headers are excerpts of the first captured user message, capped at 160 characters, with a client/short ID fallback. They are not provider-supplied conversation titles. The header tooltip explains the evidence or fallback. No extra network/LLM requests are made.
- Missing identity falls back to a request group, rather than claiming that unrelated events belong to one conversation. Compacting/rewriting message history can break inferred continuity; an explicit caller ID is more reliable. Correlation cannot outlive Monitor eviction/clear. The UI shows up to the existing 500-event limit, so groups contain the visible retained history.
- Payload-disabled captures retain no conversation IDs, titles, or history fingerprints. Fingerprints are SHA-256 hashes kept only with retained events, bounded to 2048 messages per request and charged against Monitor's memory budget.

- The toolbar uses a Filter-style ordering popover, with an ordering icon and the selected `By timestamp` or `By conversation` label.
- In timestamp order, relationship dots toggle the conversation filter (including keyboard activation) without selecting a different event. The existing dismissible filter chip reflects the same state. Connectors and dots are translucent; singleton selections have no standalone left stripe.
- In conversation order, a visible selected event anchors the list viewport during live updates. Group ordering still follows latest activity; scroll compensation happens before paint, bounded by the available scroll range. Manual scrolling updates the anchor, and scrolling away does not pull the reader back. Layout snapshots include scrollTop so arrivals before a pending scroll event are handled correctly.
